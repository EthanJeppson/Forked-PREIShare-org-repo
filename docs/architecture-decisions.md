# PREIshare investor dashboard shell: architecture decisions

**Date:** 2026-11-13
**Scope:** the Sprint 3 dashboard shell only. Each entry records what was decided and what that costs.

These entries are numbered D1 to D5 so they are not confused with the Sprint 2 listing-types decision in [`decisions/ADR-001-investor-listing-types.md`](decisions/ADR-001-investor-listing-types.md).

Everything described here is built on **mock data**. Supabase auth, live portfolio data, pgvector search and GitHub Actions CI are **not built**; they are listed in [Next sprint foundations](#next-sprint-foundations-not-built).

Related: [`sprint3-handoff.md`](sprint3-handoff.md) (what shipped and how to demo it), [`dashboard-routing-plan.md`](dashboard-routing-plan.md), [`dashboard-component-architecture.md`](dashboard-component-architecture.md).

## D1. Routing: file-based layout route with four child pages

**Context.** The brief asks for four areas (Overview, Portfolio, Deals, Profile) that share one frame (navigation, header, main region). The app already uses TanStack Router's file-based routing, where files in `src/routes/` become URLs and `src/routeTree.gen.ts` is generated from them. Early notes used `src/routes/dashboard/route.tsx` for the layout; the routing plan and the working code use `src/routes/dashboard.tsx`.

**Decision.**

- `src/routes/dashboard.tsx` is the layout route for `/dashboard`. It renders `<AppShell><Outlet /></AppShell>`.
- Children live in `src/routes/dashboard/`: `index.tsx` (`/dashboard`, Overview), `portfolio.tsx`, `deals.tsx`, `profile.tsx`.
- Recent activity is a list on Overview, not its own route. There are exactly four dashboard areas.
- `src/routeTree.gen.ts` is generated by the dev server and by `npm run build`. It is never edited by hand.

**Consequences.**

- The frame is defined once. Child pages only render their own content, so adding a page means one route file and one `nav-config.ts` entry.
- Having both `dashboard.tsx` and `dashboard/route.tsx` produces a duplicate `/dashboard` route id. Keep only `dashboard.tsx`.
- Route types are only as fresh as the generated file. If `npm run typecheck` complains about a new route, run `npm run build` or `npm run generate-routes` first.
- Nothing guards these routes. Access control is not part of this decision (see foundations table).

## D2. AppShell owns the frame and the mobile menu state

**Context.** The dashboard needs a header, a sidebar on large screens, a menu on phones, a skip link, and one `<main>`. If each page rendered its own frame, the frame would drift and each page would need its own title and menu logic.

**Decision.** `AppShell` (`src/components/dashboard/AppShell.tsx`) is the only component that composes the frame.

- It renders the skip link, `Header`, `Sidebar`, `MobileNav` and the single `<main>`.
- It owns the "mobile menu is open" state and passes it down. `Sidebar`, `Header` and `MobileNav` are presentational.
- It picks the page title for the current URL from `navConfig` and passes it to `Header`, which renders it as the page's `h1`. Pages do not render their own `h1`.
- It holds no session and no data. The "Investor (demo)" label in `Header` is a placeholder.

**Consequences.**

- One `h1` and one `main` per page, always in the same place.
- A page that needs a custom title must change `nav-config.ts` or `AppShell`, not render its own heading.
- Shared state for the frame lives in one file, so future work (a focus trap, a signed-in user) has one place to land.
- `AppShell` currently knows about the whole nav. If the shell grows, the title lookup is the first thing to move.

## D3. One navigation config, with exact link matching

**Context.** Labels and paths would otherwise be copied into the sidebar, the mobile menu and the title lookup, and could disagree. Also, TanStack Router's `Link` marks a link active by URL prefix, so a link to `/dashboard` would count as active on every child page.

**Decision.**

- `src/components/dashboard/nav-config.ts` exports `navConfig`, the only place that defines nav `label`, `to` and `pageTitle`, in display order: Overview, Portfolio, Deals, Profile.
- `Sidebar`, `MobileNav` and the title lookup all read from it.
- Every nav link uses `activeOptions={{ exact: true }}`, so Overview is active only on `/dashboard` and the current page's link carries `aria-current="page"`.

**Consequences.**

- Renaming a page or changing its URL is a one-file edit (plus the route file).
- `NavItem.to` is a plain `string`, so a typo in a path is not caught by the type checker. Check new entries by clicking them.
- Exact matching means a future nested route (for example `/dashboard/portfolio/123`) would not mark Portfolio as active. Revisit the rule when one is added.
- `AppShell` matches the title by exact path (ignoring a trailing slash) and falls back to "Dashboard" for an unknown path.

## D4. Mock data is isolated in one module and passed in as props

**Context.** The sprint is a shell: no database, no API, no auth. It still has to look like a dashboard and be easy to switch to real data later. The Deals page also has to follow a product rule: only `active` and `under_contract` listings are investor-visible, spelled as in `src/types/listing-status.ts`.

**Decision.**

- All dashboard mock data lives in `src/mock/dashboard-data.ts`. Exports are named `MOCK_*`, `Mock*` or `getMock*`, and the file opens with a "MOCK DATA ONLY" notice.
- Widgets in `src/components/dashboard/` take props. They do not fetch, and they do not import from `src/mock/`. The route files are the only place that connects mock data to widgets.
- Deals reuses the Sprint 2 `InvestorListing` type and `src/fixtures/sample-investor-listings.ts`. `getMockDeals()` filters to `active` and `under_contract`.
- Portfolio holdings and the profile have no real type yet, so `MockHolding` and `MockProfile` are mock-only shapes.
- Numbers that appear twice are derived, not typed twice (for example Overview "Open deals" is `getMockDeals().length`).
- Every dashboard page carries a visible "Mock data" label (header badge, plus a note on the table and deals list).
- Currency and label formatting live in `src/lib/format.ts`, so widgets receive plain values.

**Consequences.**

- Swapping in real data means changing where each route gets its props (a loader or server function) and deleting the mock constants. The widgets should not need to change.
- Some mock numbers are still typed by hand (the $6,850,000 total, the 45%/55% split, activity rows). They agree today (`docs/verification-checklist.md`, M7) but nothing enforces it.
- `MockHolding` and `MockProfile` are not the real shapes. Treat them as throwaway.
- The Deals list has two rows because only two sample listings are investor-visible. The brief expects about three to five.
- The Overview metric values are still strings in `MockMetric`, which is fine for display but not for real calculation.

## D5. Responsive and accessibility baseline

**Context.** The brief requires no sideways scrolling and a reachable four-area navigation at about 375px. The team also wanted keyboard and screen-reader basics in from the start rather than retrofitted.

**Decision.**

- Layout uses Tailwind utilities plus shared rules in `src/styles/dashboard.css`, imported by `src/styles.css` and scoped to `.dashboard-shell` so the starter pages are unaffected.
- Breakpoints: under 768px the sidebar is hidden and the header Menu button opens `MobileNav`; 768 to 1024px a narrower always-visible sidebar; over 1024px a full-width sticky sidebar.
- Card grids collapse to one column on phones. Wide tables scroll inside a `dashboard-table-wrap` container, so the page itself does not scroll sideways.
- Accessibility baseline: a skip link; one `h1` and one `main` per page; `aria-current="page"` on the active link; a Menu button with `aria-expanded`, `aria-controls` and a label that changes between "Open" and "Close navigation menu"; a visible `:focus-visible` ring; reduced-motion respected; the mobile panel closes on Escape, outside tap, Close button and link choice.
- Touch targets in the nav and Menu button are at least 44px high.

**Consequences.**

- This was checked with scripted headless Chrome at 375, 768 and 1280px, not on real devices or in other browsers, and not with a screen reader.
- `MobileNav` does not trap focus. The skip link is the 8th tab stop because the site header precedes the dashboard shell.
- The site header and footer from `src/routes/__root.tsx` still wrap the dashboard, which is an open product decision.
- Any new dashboard page must reuse these classes and the one-`h1`/one-`main` rule, or the baseline erodes silently. There is no automated check for it yet.
