# PREIshare — Data model and RLS policy matrix

## Purpose

Design-only blueprint for sponsor auth and property listings: which tables exist, which column links a listing to its sponsor, and exactly who may do what. It contains no SQL. Any migration must follow this document; do not add tables or open policies without updating this file first.

This matrix describes the schema **as it already exists** in `supabase/migrations/20250321000000_sponsors_properties_rls.sql` (shipped in Sprint 4 as `20250321000000_property_listings.sql`; renamed to the Sprint 5 lesson path with the same version prefix and the same SQL). If this file and that migration ever disagree, stop and flag it to the director before changing either one.

Related: `docs/data-model/property-listings-schema.md` (longer Sprint 4 design, still labelled "design only" and still using the older policy names `listings_*_own`) and `docs/data-model/rls-policy-review.md` (review notes).

## Actors and identities

| Actor | How identity is established | Notes |
| --- | --- | --- |
| Anonymous visitor | No Supabase session. | Must not read or write listings. The table grants nothing to the `anon` role. |
| Sponsor (authenticated) | Supabase Auth user; `auth.uid()` is their user id, read from the access token on every request. | May manage only rows they own. Today "sponsor" means any signed-in account; there is no sponsor role (see Open questions). |
| Service role / server admin tasks | Secret service-role key, server only. | Not used from the browser. **No code reads it today.** It bypasses RLS, so it is never used for sponsor reads and writes. |

## Tables

### Sponsor linkage: `auth.users` (Supabase-managed, no `profiles` table)

A sponsor is one row in Supabase's own `auth.users` table. Its `id` is the value `auth.uid()` returns for that signed-in person. This project adds **no** `profiles` or `sponsors` table: nothing in the current stories needs a display name or other profile data, and the dashboard's "Signed in as" line uses the account's email.

| Column | Type (intent) | Notes |
| --- | --- | --- |
| id | uuid | Same value as `auth.uid()` while that person is signed in. Managed by Supabase Auth. |
| email | text | Used for sign-in and for the "Signed in as" label. Managed by Supabase Auth. |

This project defines no policy on `auth.users` and does not expose it as an app table.

### `property_listings` (listings owned by a sponsor)

| Column | Type (intent) | Required | Notes |
| --- | --- | --- | --- |
| id | uuid (PK) | yes | Generated by default. Cannot be changed after creation. |
| owner_id | uuid, foreign key to `auth.users.id` | yes | **RLS hinge column.** Must equal `auth.uid()` for every owner rule. Cannot be changed after creation. Deleting an account that still owns listings is refused. |
| title | text | yes | Listing title. Dashboard card heading. |
| summary | text | yes | Short description. |
| property_type | text | yes | One of `single_family`, `multi_family`, `commercial`, `land`. |
| status | text | yes | One of `draft`, `active`, `under_contract`, `closed`. Defaults to `draft`. Dashboard card badge. |
| address_line1 | text | yes | Street address. |
| address_line2 | text | no | Unit or suite. |
| city | text | yes | Dashboard card location. |
| region | text | yes | State or region. |
| postal_code | text | yes | |
| country | text | yes | Two capital letters, defaults to `US`. |
| asking_price | numeric(14,2) | no | Must be greater than zero when present. Stored in dollars and cents. |
| closed_at | timestamptz | no | Set if and only if `status` is `closed`. |
| created_at | timestamptz | yes | Defaults to now. Cannot be changed after creation. |
| updated_at | timestamptz | yes | Refreshed by the database on every update. |

Other rules the table enforces (not RLS, but they keep rows valid): the allowed values above, a positive price, `closed_at` matching `closed` status, and an index on `owner_id` so owner lookups stay fast.

## RLS posture

- RLS is enabled on `property_listings` before any API access.
- The table starts with every privilege revoked, then grants SELECT, INSERT, UPDATE and DELETE to the `authenticated` role only. The `anon` role gets nothing. TRUNCATE is never granted because it ignores RLS.
- No policy uses `USING (true)` for any role. No policy lets one account read another account's rows.
- Browser clients use the anon key plus the signed-in user's token only. Never the service role.
- Server code that reads or writes listings acts as the signed-in user so these rules apply.

## RLS policy matrix

"Rule shape" is the comparison the policy makes, not SQL to copy.

| Table | Operation | Who | Rule (plain English) | Rule shape | Policy name in the migration |
| --- | --- | --- | --- | --- | --- |
| property_listings | SELECT | Authenticated sponsor | Can read only listings they own. | `owner_id = auth.uid()` | `property_listings_select_own` |
| property_listings | INSERT | Authenticated sponsor | Can insert a listing only if they are the owner on the new row. | `WITH CHECK owner_id = auth.uid()` (the app also sets `owner_id` from the session) | `property_listings_insert_own` |
| property_listings | UPDATE | Authenticated sponsor | Can update only listings they own, and the row must still be theirs afterwards, so a listing cannot be handed to someone else. | `owner_id = auth.uid()` before and after | `property_listings_update_own` |
| property_listings | DELETE | Authenticated sponsor | Can delete only listings they own. | `owner_id = auth.uid()` | `property_listings_delete_own` |
| property_listings | SELECT, INSERT, UPDATE, DELETE | Anonymous visitor | No access. No policy and no grant for `anon`. | None | None |
| property_listings | Any | Authenticated, but not the owner | No access to rows owned by someone else. This is the Sponsor A / Sponsor B rule. | Falls out of the four rows above | None |
| auth.users | Any | Sponsor via the app | Not an app table. This project adds no policy and no code reads it directly. | None | None |

Extra guard outside RLS: a database trigger refuses any update that changes `id`, `owner_id` or `created_at`, and refreshes `updated_at`.

## Requirement → design mapping

Each row quotes or paraphrases a line from `docs/sponsor-auth-requirements.md`.

| Requirement | Satisfied by |
| --- | --- |
| Story 1: sponsor signs in with email and password so the app knows who I am. | Supabase Auth account in `auth.users`; its `id` is `auth.uid()`. |
| Story 2: after sign-in I see only my properties, never another sponsor's. | SELECT row: `owner_id = auth.uid()`; owner filter in `src/server/listings.ts`. |
| Story 3: I can create a property owned by my account without choosing the owner. | INSERT row: `WITH CHECK owner_id = auth.uid()`; the form has no owner field and the server ignores any owner sent by the browser. |
| Story 4: an anonymous visitor cannot open the dashboard or change listings. | No `anon` grant or policy on `property_listings`. The route guard is a second layer. |
| Non-goal: no public (anonymous) create, update or delete. | Anonymous row of the matrix: no access. |
| Non-goal: no admin console or cross-sponsor moderation. | No admin policy. Service role is not used by any code. |
| Non-goal: no investor browsing of sponsors' listings. | No cross-account SELECT policy. |
| Success criterion: lists return only rows the signed-in sponsor may see. | SELECT row. |
| Success criterion: create associates the new row with the signed-in sponsor. | INSERT row and the `owner_id` column. |
| Success criterion: access is enforced by RLS, not only by hiding buttons. | RLS posture section: RLS enabled, four own-row policies, `anon` revoked. |
| Success criterion: browser config uses only public keys. | Matrix assumes browser = `authenticated` role only; env split is in `docs/env-var-checklist.md`. |
| Threat: guessing another sponsor's property id. | SELECT, UPDATE and DELETE rows deny a row you do not own even when the id is known. |
| Threat: leaked service-role key. | Service-role row in Actors: server only, unused. |
| Threat: "security by hiding buttons". | Rules live in Postgres, not in React. |
| Dashboard card fields. | `title`, `city`, `region`, `property_type`, `status`, `asking_price`, `created_at` on `property_listings`. |

## Out of scope this sprint

- Public marketplace read of listings (would need a separate, intentional SELECT policy).
- Investors reading sponsors' listings.
- Multi-sponsor or team ownership of one property.
- Admin or approver override, and any use of the service role for normal reads and writes.
- A `profiles` table, a sponsor role, and sign-up policy (open, invite-only, email confirmation).
- Richer fields (contacts, ownership, IRR, cap rate), images, documents, search.

## Open questions for review

- [ ] **Profiles.** Do you want a `profiles` table (for example a display name) linked to `auth.users`, or is `auth.users` enough? Not decided; none exists.
- [ ] **"Signed in" is not "sponsor".** Any signed-in account can create listings today. Should sponsors become a distinct role?
- [ ] **DELETE.** The database allows an owner to delete their own rows, but no server function or screen does. Keep hard delete, switch to soft delete (for example a status), or remove the delete policy?
- [ ] **Status changes.** A sponsor can set any status on their own listing. Should some moves, such as approval, need another role later?
- [ ] **Policy names in older docs.** `docs/data-model/property-listings-schema.md` still says `listings_*_own`; the migration uses `property_listings_*_own`. Fix that doc in a later change.
