# Property Listings Data Model & Auth Boundaries

> Sprint 4 design document for PREIshare. This is the blueprint the migration step must match. It contains no SQL on purpose.
>
> Inputs: [`../requirements/sponsor-auth-and-listings-brief.md`](../requirements/sponsor-auth-and-listings-brief.md) (wins on conflict), [`../setup/supabase-env-checklist.md`](../setup/supabase-env-checklist.md), and the existing listing types in `src/types/` (see [`../decisions/ADR-001-investor-listing-types.md`](../decisions/ADR-001-investor-listing-types.md)).
>
> **Status:** design only. No table, policy, Supabase client or login page exists yet. The dashboard still shows mock data.

## 1. Purpose

Signed-in sponsors manage **real** property listings stored in PostgreSQL. A sponsor sees and changes only their own listings. Nothing is kept in a client-side array, and the service-role key never reaches the browser.

## 2. Entity: `property_listings`

One row is one property listing. The table maps to the existing `InvestorListing` type (`src/types/investor-listing.ts`): same meaning, with the nested `address` and `financials` groups flattened into plain columns and names written in `snake_case`.

| Column | Type (Postgres) | Nullable | Maps to (`InvestorListing`) | Notes |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | no | `id` | Primary key. Generated by the database. Never reused or changed. |
| `owner_id` | `uuid` | no | (new) | The sponsor who owns this row. Foreign key to `auth.users(id)`. See section 3. |
| `title` | `text` | no | `title` | Short display name. |
| `summary` | `text` | no | `summary` | Short plain-text description of the opportunity. |
| `property_type` | `text` | no | `propertyType` | One of `single_family`, `multi_family`, `commercial`, `land`. |
| `status` | `text` | no | `status` | One of `draft`, `active`, `under_contract`, `closed`. Defaults to `draft`. |
| `address_line1` | `text` | no | `address.line1` | Street number and name. |
| `address_line2` | `text` | yes | `address.line2` | Unit, suite or floor. |
| `city` | `text` | no | `address.city` | |
| `region` | `text` | no | `address.region` | State, province or region. |
| `postal_code` | `text` | no | `address.postalCode` | Text, so leading zeros survive. |
| `country` | `text` | no | `address.country` | Two-letter uppercase code. Defaults to `US`. |
| `asking_price` | `numeric(14,2)` | yes | `financials.askingPrice` | Whole dollars and cents, USD only. When present it must be greater than zero. Nullable because `financials` is optional in the existing types. |
| `closed_at` | `timestamptz` | yes | `closedAt` | Set only when `status` is `closed`, and then required. |
| `created_at` | `timestamptz` | no | `createdAt` | Defaults to now. Set once. |
| `updated_at` | `timestamptz` | no | `updatedAt` | Defaults to now. Bumped on every update. Never earlier than `created_at`. |

### Rules the table itself should enforce

- `status` and `property_type` accept only the listed values (a check rule on a text column is recommended over a Postgres enum, because it is easier to change later).
- `asking_price`, when present, is greater than zero.
- `closed_at` is present exactly when `status` is `closed`. This mirrors the existing type, where only a closed listing has `closedAt`.
- `updated_at` is not earlier than `created_at`.
- Currency is USD only, so there is no currency column until a second currency is needed.

### Deliberately left out of the first version

- `contacts` and `ownership` (nested lists in `InvestorListing`). The brief leaves open how much the first create form collects (brief, open question 3). This design proposes the smaller set above.
- `projectedIrrPercent` and `capRatePercent`.
- Images or other media, documents, search or embeddings (pgvector), and shared ownership between sponsors.

### Indexes (recommended)

- Primary key on `id`.
- An index on `owner_id`, because every sponsor query filters by owner and every RLS check compares it.
- Nothing else until a real query needs it.

### Field names differ from the scaffold, on purpose

A generic listings example would use `draft` / `published` / `archived` and a `description` column. This repo already ships `draft`, `active`, `under_contract`, `closed` (`src/types/listing-status.ts`), and the Sprint 3 brief says to spell them exactly that way. The older `docs/domain/` files still list five other statuses; `ADR-001` records that the code wins until those docs are updated. This design follows the code.

## 3. Ownership model

- Every row has a required `owner_id` that holds the Supabase Auth user id (`auth.users.id`) of the sponsor who created it. It cannot be null.
- `owner_id` is a foreign key to `auth.users(id)`. Choice made here: `ON DELETE RESTRICT`. A sponsor account cannot be deleted while it still owns listings, so listing data is never silently destroyed. (Cascade would delete them. Account deletion is out of scope this sprint, so the stricter option costs nothing today.)
- On create, the server sets `owner_id` from the verified session. The browser never sends it, and a value sent by the browser is ignored. The database also rejects an insert whose `owner_id` is not the caller's id (section 4), so a mistake in app code cannot create a row for someone else.
- `owner_id` is never edited after creation. Moving a listing to another sponsor is out of scope.
- "Owner" here means the sponsor **account** that owns the record. It is not the same as `ownership.ownerName` in the existing type, which names who owns the *property*.

## 4. Row Level Security (RLS), plain language

Row Level Security is Postgres deciding, row by row and for each request, whether the caller may touch a row. The caller's identity comes from the sign-in token, read inside Postgres as `auth.uid()`.

**RLS is enabled on `property_listings`. Without a matching policy, nothing is allowed.** The logged-out (`anon`) role gets no access to this table at all.

| Policy (suggested name) | Command | Who | Rule in plain words |
| --- | --- | --- | --- |
| `listings_select_own` | SELECT | signed-in users | A sponsor can read a row only if `owner_id` equals their own `auth.uid()`. |
| `listings_insert_own` | INSERT | signed-in users | A sponsor can insert a row only if the new row's `owner_id` equals their own `auth.uid()` (the "with check" part). |
| `listings_update_own` | UPDATE | signed-in users | A sponsor can update only rows they own (the "using" part), and after the update `owner_id` must still be their own (the "with check" part), so a row cannot be handed to someone else. |
| `listings_delete_own` | DELETE | signed-in users | A sponsor can delete only rows they own. |

What this means for the people in the brief:

- **Sponsor:** sees, creates (and, if enabled, edits) only their own listings. Sponsor A cannot see Sponsor B's rows, even by calling the database API directly with A's session.
- **Unauthenticated visitor:** no access to any listing row.
- **No public "read all" policy.** The brief gives investors no way to browse listings this sprint, so nothing here grants world-readable or cross-sponsor access. Adding one needs a written decision first.
- **Service-role key:** bypasses RLS entirely. It is not used for any sponsor operation (section 5).

Scope note: the brief puts editing and deleting out of scope for Sprint 4 (create and read only). The four rules are written down now so the security shape is settled in one place. Whether the migration creates the UPDATE and DELETE policies this sprint is open question 3 below. Leaving a policy out is safe, because no policy means no access.

## 5. Server vs browser operation map

| Operation | Runs where | Client / key | Notes |
| --- | --- | --- | --- |
| Sign up, sign in, sign out | Supabase Auth, started from the app | Public client: `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`. No service-role. | Anon key is public by design. Sign-up policy is open (brief, question 4). |
| Check the session before a protected page | Server (route guard on `src/routes/dashboard.tsx`, via `createServerFn` or `beforeLoad`) | Server client acting as the user | No session means redirect to sign-in. |
| List my listings | Server loader | Server client acting as the user (`SUPABASE_URL` + the user's session). RLS applies. | Result is passed to prop-driven widgets as props. |
| Create listing | Server function | Server client acting as the user. `owner_id` comes from the verified session. | Validate every field on the server. RLS is the second line of defence. |
| Update or archive listing | Server function (if enabled) | Server client acting as the user | RLS blocks cross-owner edits. |
| Delete listing | Server function (if enabled) | Server client acting as the user | Same. |
| Anything needing `SUPABASE_SERVICE_ROLE_KEY` | Server only | Service-role | **None planned this sprint.** If one appears it needs a written reason, and the key is read with `process.env` inside a server function, never in browser code. |

Rules that follow:

- **The service-role key never appears in client code, a `VITE_*` variable or a committed file.** See the server-only boundary in the brief and the variable table in the env checklist.
- Browser code uses only the URL and anon key, and RLS protects the data.
- No listing data comes from `src/fixtures/` or `src/mock/` on the sponsor pages. Those files stay as they are for the mock-labelled pages.

## 6. Out of scope for this sprint

- Contacts, ownership lists, IRR and cap-rate fields; images, documents, payments.
- Admin or listing-editor roles; any screen that manages other people's listings.
- Investors browsing listings; any public or cross-sponsor read policy.
- Search, filtering, embeddings (pgvector).
- Moving a listing between sponsors, shared ownership, deleting accounts.
- Seeding the database from the mock fixtures.

## 7. Acceptance checks for the migration step

- [ ] A `property_listings` table exists with exactly the columns, types and nullability in section 2.
- [ ] `owner_id` is `not null` and a foreign key to `auth.users(id)`.
- [ ] The value rules in section 2 are enforced by the database (status, property type, price, `closed_at`, timestamps).
- [ ] RLS is enabled, and the SELECT and INSERT own-row policies in section 4 exist. The UPDATE and DELETE policies exist if open question 3 is answered yes.
- [ ] The INSERT policy checks `owner_id = auth.uid()` on the new row.
- [ ] No policy grants access to `anon`, and no policy lets one sponsor read another's rows.
- [ ] A test with two accounts shows Sponsor A cannot read, insert as, or (if enabled) change Sponsor B's rows.
- [ ] The schema exists as a committed migration file, not as dashboard clicks.
- [ ] No migration, doc or example file contains a real key.

## 8. Open questions (for the director; not decided here)

1. **How much does the first create form collect?** This design proposes: title, summary, property type, address, optional asking price, status defaulting to `draft`. Contacts and ownership are left for later. Confirm, or add fields. (Brief, question 3.)
2. **Can a draft be saved incomplete?** The older domain docs say a draft only needs a title, status and property type. This design makes the address and summary required on every row, so a draft cannot be saved before they are known. Relaxing that means making those columns nullable and adding a rule that investor-visible statuses need them.
3. **Create the UPDATE and DELETE policies this sprint?** The brief says create and read only. The rules are written; the choice is whether the migration includes them, with no UI yet. Recommended: include them, since they are the same own-row shape and are safe.
4. **Can an `active` listing have no price?** `asking_price` is nullable because `financials` is optional in the types (`ADR-001` already flags this).
5. **What happens to the Deals page?** It shows investor-visible mock listings. Showing real listings to investors would need a cross-sponsor read policy, which this design does not add. Either Deals stays mock and is labelled so, or a new decision defines investor access. (Brief, questions 1 and 2.)
6. **Where do sponsor pages live?** The brief says "inside the existing dashboard shell" but names no route. The UI step decides.
7. **How does the server see the session?** Server functions need the user's session. The usual way is Supabase's separate server helper package, which the brief does not pre-approve (it allows only the Supabase client as a new dependency). The alternative is to pass the access token from the browser to each server function. Decide in the client-wiring step.
8. **Sign-up policy and soft delete.** Open sign-up, invite-only or email-confirmed (brief, question 4); and whether `archived` or a `deleted_at` column is wanted later.
